- **Auth hardening — optional JWT issuer/audience binding (#842).** `create_access_token`
  and `decode_token` now accept `issuer` / `audience`; when a `DUTCHBAY_JWT_ISSUER` /
  `DUTCHBAY_JWT_AUDIENCE` is configured, issued tokens carry the `iss` / `aud` claim and
  validation requires an exact match (a valid-signature token minted for a different
  issuer/audience is rejected 401 — cross-audience replay defence). Unset ⇒ neither
  stamped nor enforced, so the binding is opt-in and backward-compatible. Existing token
  hardening is unchanged (HS256 pinned, `alg:none`/alg-confusion rejected, `exp` enforced,
  constant-time signature check, fail-closed signing secret, timing-equalised user
  enumeration). Per-user run isolation on the async job path (the only per-user
  report-read surface — `JobRecord.result` via owner-scoped `GET /jobs/{id}`) is verified
  by an added result-payload isolation test; the synchronous `/cases/report.*` routes
  persist no per-user state. Config-first, no secrets in code; KPI-neutral (auth/API only).
