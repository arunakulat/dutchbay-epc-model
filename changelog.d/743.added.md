- **Solar resource provenance and realism (#743, all opt-in / default-off / byte-identical).**
  Three independent additions to the (validation-only) `solar_resource` producer chain, none
  of which changes any committed scenario's economics — the KPI oracle stays byte-identical
  on `dutchbay_lendercase_2025Q4.yaml` and `dutchbay_hybrid_windsolar_2025Q4.yaml`:
  - **Graded source-quality provenance** — `solar_resource.source_quality` grades the resource
    evidence behind a modelled solar P50 (measurement type, years of record, named TMY dataset)
    into a 0-1 `quality_score` + A/B/C/D grade, emitted into the `solar_resource` provenance
    block (the photovoltaic analogue of the wind `provenance.aep`). Pure METADATA: it drives no
    capacity factor and no haircut; even a grade-A config leaves the billed CF untouched. A
    scenario declaring no `resource.solar.source_quality` block records a candid default grade.
  - **SOLAR-9 bifacial-in-chain discipline guard** — `solar_resource.bifacial_guard` promotes
    the SOLAR-9 doc note to an ENFORCED validation: the OVERWRITE finance bridge
    (`solar_export_to_scenario_patch`) now refuses a bifacial rear-side uplift from entering the
    financed CF chain, keeping the committed lender pack monofacial. A no-op on every committed
    scenario (none declares bifacial); the illustrative
    `scripts/generate_solar_assessment_report.py` sets `project.capacity_factor` directly and
    bypasses this bridge, so its disclosed `cf_mono`/`cf_bifacial` side-by-side is untouched.
  - **Optional time-varying soiling profile** — an OPTIONAL `resource.solar.soiling_profile`
    block (`solar_resource.soiling_profile`; accumulation rate + wash cadence + optional clean
    floor / saturation cap) whose energy-weighted effective soiling replaces the flat static
    soiling in the producer's loss path. Opt-in like the `resource.solar.uncertainty` block
    (#604): a scenario without it is byte-identical to the flat-soiling behaviour. Applying a
    profile to move the committed solar CF is a producer-driven re-baseline (user gate, same
    class as #529 SOLAR-6/12) and is NOT applied to any committed scenario.
