# DutchBay EPC Model — Module Reference

This document is the single, complete per-module reference for the DutchBay EPC model. For
each top-level package and its notable modules it states the **purpose** (what it does), the
**design reasoning** (why it exists and where it sits in the architecture), the **academic or
methodological grounding** where any is cited in the code, and the **interfaces, optional
extras, and limitations** the code itself discloses.

- **Scope.** Describes the code at version 15.3.0 (repository `main` at commit `3012641`).
- **Audience.** Developers, model reviewers, and lender/DFI technical due-diligence readers.
- **How to read.** Each section follows a fixed structure: path(s), purpose, design reasoning,
  a key-modules table, academic grounding, and interfaces/limitations. Standards and methods
  are cited only where the code actually references them.
- **Companion documents.** The [Development Guide](DEVELOPMENT.md) covers setup and workflow;
  the register `DutchBay_TechDebt_Register_2026-07-11.md` and the deep-research credibility
  report (both delivered separately) cover code health and external methodology validation.

## Architecture at a glance

The model is organised as a deterministic finance core wrapped by analytics layers, fed by
optional resource producers, and surfaced through a web/report layer.

- **Configuration in, KPIs out.** A scenario YAML (`scenarios/*.yaml`) is validated by the
  strict schema guard (`analytics/schema_guard.py`), loaded, and evaluated through the single
  gateway `analytics.evaluation_v14.evaluate_with_overrides`. The gateway drives the
  deterministic finance engine (`finance/`: cashflow, then debt sizing, then tax, then
  returns) to produce a flat KPI dictionary (project and equity IRR, NPV, DSCR/LLCR/PLCR).
- **Resource producers are offline and frozen.** The wind (`wind_resource/`) and solar
  (`solar_resource/`) pipelines run separately and hand the finance stack a frozen AEP export,
  so a lender finance run needs no Copernicus or pvlib credentials.
- **Analytics wrap the gateway.** Monte Carlo (`analytics/mc/`), global sensitivity
  (`analytics/sensitivity/`), the CASPER lender risk blocks (`analytics/casper/`), and FX
  (`analytics/fx/`) all evaluate through the gateway rather than reaching into the engine.
- **One presentation of one result.** The web service (`app/`) and the report layer
  (`app/reports/`) render the same computed results as an HTML or PDF lender report.

Three structural rules hold the architecture together and are enforced by lint tests:
IRR/NPV are defined only in `finance/irr.py` and WACC only in `finance/wacc_v14.py`
(ARCH-02); every analytics result type is defined in `analytics/contracts_v14.py` and consumed
through the gateway (ARCH-04/CCCDIR); and all parameters live in configuration, validated
strictly before any evaluation (CESSPIT).

## Entry Points & Root Modules

**Path(s):** `run_full_pipeline_v14.py`, `run_scenario_analytics_v14.py`, `constants.py`, `dutchbay_bootstrap.py`, `dutchbay_bootstrap_rules.py`, and the Hydra analytics entrypoints `analytics/cli/cli_monte_carlo_hydra.py`, `analytics/cli/cli_sensitivity_hydra.py`, `analytics/cli/cli_capital_structure_optimize_hydra.py` (with package docstring `analytics/cli/__init__.py`).

**Purpose:** The command-line surface of the model — the blessed Hydra entrypoints that a user, CI lane, or the web service invokes to run the canonical wind-to-finance pipeline, batch scenario comparison, Monte-Carlo, sensitivity, and capital-structure optimization, plus the repo-hygiene bootstrap and the single immutable-constants module.

**Design reasoning:** These files are deliberately thin wrappers that parse Hydra config and delegate to engine functions, keeping business logic out of the CLI layer (GWTF R3 Hydra-only, argparse banned; CLI-03 JSON-first output). They honor the config-first contract (ARCH-01, CCCDIR): every default, threshold, and business value lives in `config/defaults.yaml` / `scenarios/*.yaml` / `conf/*.yaml`, and `constants.py` holds only universal physical constants. A key structural decision is the explicit split between the canonical single-scenario engine (`run_full_pipeline_v14.py` → `analytics.pipeline_v14_enhanced.run_v14_pipeline`, build-up WACC, two-pass interest tax shield, equity waterfall, full `ScenarioResult`) and the deliberately lighter batch-comparison path (`run_scenario_analytics_v14.py`), which stamps a machine-readable `basis="comparison_snapshot"` provenance marker so batch DSCR/IRR can never be mistaken for lender-grade numbers. Optional and report dependencies are imported lazily behind opt-in flags (CASPER call-time guarding), so the base finance CLI never pulls in the wind/solar/report stacks unless explicitly asked.

### Academic / methodological grounding

The entry-point layer is orchestration and contract plumbing; it carries no methods of its own. It references two standards only in docstrings/comments that describe the downstream engines it invokes (the actual implementations live outside this domain):

- `run_full_pipeline_v14.py` — IEC 61400-15-2 (named at line 527 in the description of the `uncertainty.*` energy-yield uncertainty budget / P50 haircut applied by the wind-resource path) and Iman–Conover / Latin Hypercube Sampling (named at line 767 describing the canonical MC engine `analytics.mc.engine` it can drive). These are pointers to the wired engines, not grounding realized in this file.

No other module in this domain (`run_scenario_analytics_v14.py`, `constants.py`, the bootstrap pair, or the three Hydra CLIs) cites a standard, method, or paper in-code — they delegate any such method to `analytics.mc.engine`, `analytics.core.sensitivity_runner`, and `analytics.capital_structure_optimizer_v14`.

### Interfaces, optional extras, and limitations

- **Consumes:** scenario/`conf` YAML via Hydra `key=value` overrides; optionally frozen wind/solar assessment JSON exports (`wind_assessment_json` / `solar_assessment_json`). **Produces:** JSON to stdout as the primary contract (CLI-03), with optional file artifacts (`summary.json`, `kpis.json`, `debt_result.json`, `equity_distribution.json`, `annual_rows.csv`, Excel workbooks, and opt-in HTML lender reports).
- **Opt-in install extras:** the `[wind]` extra powers `wind_auto_orchestrate` (probed before subprocessing, fails fast on `ImportError`); the `[solar]` physics freeze sits behind the `[solar]` extra (the finance path never imports `pvlib` or calls `compute_solar_aep` — solar parity is by frozen export only, #614); the report/workbook and capital-risk emitters lazily import a jinja/matplotlib/weasyprint stack only when their default-off flags are set.
- **Default-off levers the code discloses:** wind and solar ingestion are both OFF by default (omitting the inputs preserves pre-Sprint-19 behaviour exactly); `emit_capital_risk_report` (#779) and the capital-structure optimizer CLI are both off/out-of-pipeline so committed scenarios remain byte-identical; `run_scoped` (#735) defaults false → output paths byte-identical.
- **Honesty boundaries:** `run_scenario_analytics_v14.py` stamps `basis="comparison_snapshot"` and uses an informational (non-build-up) discount rate — it is explicitly NOT the authoritative economics path; use `run_full_pipeline_v14.py` for a single scenario's lender-grade numbers. The Monte-Carlo CLI degrades its status to `degraded`/`degenerate` rather than reporting fabricated toy-fallback metrics as clean success.
- **Limitations:** Hydra INFO job logging may precede the JSON on stdout for the sensitivity and optimizer CLIs — consumers must parse from the first `{` line. The bootstrap modules are read-only diagnostics (no mutations); a missing/mis-pathed `DUTCHBAY_FLOW_RULESET_CSV` produces a clear error but is treated as a soft, non-fatal failure.

## Analytics Evaluation Spine (Gateway, Contracts, Orchestration, Config)

**Path(s):** `analytics/evaluation_v14.py`, `analytics/contracts_v14.py`, `analytics/pipeline_v14_enhanced.py`, `analytics/pipeline_analytics_v14.py`, `analytics/scenario_loader.py`, `analytics/scenario_analytics.py`, `analytics/evaluate_scenario.py`, `analytics/config_schema.py`, `analytics/schema_guard.py`, `analytics/optimization_v14.py`, `analytics/run_manifest.py`, `analytics/run_modes.py`.

**Purpose:** The typed spine that turns a resolved scenario configuration into a lender-grade financial result: it loads and validates config, runs the canonical v14 pipeline once per evaluation, and returns immutable result contracts that every downstream analytics layer (sensitivity, Monte Carlo, optimization, reporting) consumes. It is the single seam between the finance engine and all higher-order analytics.

**Design reasoning:** The spine exists to enforce one evaluation path (ARCH-04): sensitivity, Monte Carlo and optimization engines never call the finance core directly — they go through `evaluate_with_overrides()` in `evaluation_v14.py`, which merges overrides, validates, and delegates to `pipeline_v14_enhanced`. The gateway is deliberately import-safe: it holds NO module-scope imports of `analytics.sensitivity` or `analytics.mc` (all such enrichment imports are lazy inside functions) to break a documented circular-import chain (P1 hotfix v14.4.2). Result types are centralized in `contracts_v14.py` (CCCDIR — contracts centralized, imports explicit), config-strictness is enforced pre-flight by `schema_guard.py` against the declarative registry in `config_schema.py` (CESSPIT — config explicit, schema strict, pre-flight integrity), and reproducibility is bound by `run_manifest.py` (resolved-config SHA-256 + engine version + git SHA). IRR/NPV are not computed here — they remain isolated in `finance/irr.py` (ARCH-02); this layer only orchestrates and normalizes.

### Key modules

| Module | Role |
|---|---|
| `evaluation_v14.py` | The single evaluation gateway (ARCH-04). Exposes `evaluate_with_overrides()` (canonical entry for sensitivity/optimization — deep-merges dotted or nested overrides into base config, runs the pipeline, returns either a normalized KPI dict or the full result), `evaluate_scenario_from_dict()`, and `evaluate_with_casper_tail_risk()` (the only function permitted to import tail-risk modules, all lazily). Deep-merge produces a structurally independent config so re-merging the same base thousands of times in MC/sensitivity loops cannot leak in-place mutations (#586). |
| `contracts_v14.py` | Backward-compatible source of truth for all v14 analytics result contracts (CCCDIR). Frozen dataclasses (with a `ContractMixin` giving `model_dump()`/`dict()`) for `ScenarioResult`, `CasperResult`, `SensitivitySuite`/`TornadoResult`/`ShockResult`, `MonteCarloResult`, `WaccResult`, `TrancheDebtProfile`, `MultiTechWBS`, grid/reactive/ride-through result types, and IRR-bridge/capital-structure contracts. Deliberately dataclass-based because the canonical pipeline serializes via `dataclasses.asdict`; carries the API-visible `CASPER_CONTRACT_VERSION`. |
| `pipeline_v14_enhanced.py` | The canonical lender-grade pipeline (`run_v14_pipeline_enhanced`, aliased `run_v14_pipeline`). Orchestrates config load → schema validation → cashflow build → debt planning → build-up/config WACC → KPI computation → FX integration → equity-distribution waterfall, emitting a `ScenarioResult`. Tracks CASPER audit metadata (`PipelineMetrics`: per-stage timings, validation errors/warnings, tz-aware UTC stamps) and degrades gracefully on optional features. |
| `pipeline_analytics_v14.py` | Optional analytics overlay on the base pipeline: returns analysis (project/equity IRR/NPV/MIRR), risk metrics (VaR/CVaR/tail risk on the LKR CFADS series), tornado/sensitivity and MC hooks. Config-driven and disabled by default for backward compatibility; delegates the actual risk math to the risk/MC engines. |
| `scenario_loader.py` | Universal YAML/JSON config loader (v13/v14 compatible). Light structural checks only — does not impose v14-only sections; provides a strict FX resolver (`_resolve_fx`, `_assert_fx_spot_consistency`) that refuses to silently invent FX, and enforces AEP-provenance source registration. |
| `evaluate_scenario.py` | Thin coordinator-only entry point: load base config, apply nested overrides, call `run_v14_pipeline` once, normalize outputs to a flat KPI dict. No cashflow/debt/WACC math and no CLI concerns of its own. |
| `scenario_analytics.py` | Library-only batch orchestrator for comparing many scenarios (per-scenario discount rate, name filtering, optional parallelism, EPC/LCOS breakdown, JSON batch summary). Stamps every payload with `BATCH_ECONOMICS_BASIS = "comparison_snapshot"` to mark its lighter economics basis. |
| `config_schema.py` | Declarative registry of required config fields per logical module (`RequiredFieldSpec`: owner module, candidate YAML paths tried in order, required flag, error/warning severity). `build_schema_dataframe()` renders the registry for documentation/audit. |
| `schema_guard.py` | CESSPIT gatekeeper: `validate_config_for_v14()` is the strict-by-default pre-flight validator run before any cashflow/debt calculation — checks FX section, technology-`type` enum (ARCH-6), opt-in `run.mode`, `taxes_indirect`, and cross-field grid conditionals (Thévenin range, estimated-basis gate, per-tech grid interface), raising `ConfigValidationError` on any breach. |
| `optimization_v14.py` | Generic single-parameter optimizer facade over `evaluate_with_overrides` (#30/#602): maximize/minimize a target KPI over `[lower, upper]` subject to an optional KPI constraint (e.g. max equity IRR s.t. min DSCR ≥ covenant). Two methods: exhaustive `"grid"` (`np.linspace`) and opt-in `"bounded"` (SciPy). Composes the gateway; reimplements no finance math. |

| `run_modes.py` | Declared-intent honesty-gate contract (#733): a `RunMode` enum (`screening`/`developer`/`lender`/`ic`) plus a `RunModePolicy` table unifying scattered toy-fallback/trial-floor switches behind one declared run grade. Contract-and-validation slice; opt-in (absent config ⇒ no change). |

### Academic / methodological grounding

- `optimization_v14.py` — SciPy `scipy.optimize.minimize_scalar(method="bounded")` (Brent / golden-section scalar minimization) — used for the opt-in `"bounded"` refinement of a constrained single-parameter optimum; the docstring explicitly cautions it is a local minimizer that can converge to a local optimum on the non-convex DSCR-sculpt feasibility region, and to cross-check against a coarse grid.
- `run_manifest.py` — ICAEW audit posture / SHA-256 config hashing — reproducibility and tamper-evidence discipline (resolved-config hash + engine version + commit); a professional-audit standard reference, not an academic paper.
- The remaining modules carry no in-code academic citation: the VaR/CVaR/tail-risk and tornado methods referenced in `pipeline_analytics_v14.py` are delegated to the risk/MC engines outside this domain. Otherwise this domain is orchestration and contract plumbing with no formal academic grounding.

### Interfaces, optional extras, and limitations

- **Consumes:** scenario YAML/JSON configs (via `scenario_loader`) and override mappings (dotted `"finance.capex_usd"` or nested), plus a logical module list for validation (default `["cashflow","debt"]`). **Produces:** normalized flat KPI dicts and immutable contract objects — `ScenarioResult`, `CasperResult`, `SensitivitySuite`, `MonteCarloResult` — all `model_dump()`-serializable, plus a `RunManifest`.
- **Optional/opt-in levers disclosed in-code:** `pipeline_analytics_v14` analytics are disabled by default (backward compatibility); `optimization_v14`'s `"bounded"` SciPy path is opt-in (`method=`), with `"grid"` the default; `schema_guard`'s `run.mode`, `taxes_indirect`, `crossval` and grid-conditional validations are present-only (absent block ⇒ byte-identical, no error). No dedicated pip "extra" gates this domain; `optimization_v14` imports SciPy at module scope (hard dependency of that module, not a guarded optional).
- **Honesty boundary (batch vs canonical):** `scenario_analytics.py` stamps `BATCH_ECONOMICS_BASIS = "comparison_snapshot"` because the batch comparison path deliberately computes DSCR/IRR on a lighter basis than the canonical pipeline — no build-up WACC, no two-pass interest tax shield, no equity-distribution waterfall — so consumers cannot mistake batch numbers for authoritative `run_full_pipeline_v14.py` economics.
- **Import-safety constraint:** the gateway must remain free of module-scope `analytics.sensitivity`/`analytics.mc` imports; only `evaluate_with_casper_tail_risk()` may import tail-risk code, lazily — a structural rule that prevents the documented circular-import regression.
- **Typing caveat (self-disclosed):** `pipeline_v14_enhanced` keeps `Mapping[str, Any]`/`dict[str, Any]` at the config-in/result-out boundary; fully typed `ScenarioConfig`/`DebtResult`/`CashflowRow`/`KPIResult` models are a tracked refinement, not a current guarantee.

## Analytics Core Primitives (KPIs, Returns, Risk)

**Path(s):** `analytics/core/` — `metrics.py`, `returns.py`, `risk_metrics.py`, `covenant_breach.py`, `exceedance.py`, `parameter_solvers.py`, `sensitivity_runner.py`, `epc_helper.py` (plus the `__init__.py` re-export surface).

**Purpose:** The foundational calculation layer that turns per-scenario and Monte-Carlo cashflow outputs into board/lender KPIs — project/equity NPV and IRR, DSCR/LLCR/PLCR coverage statistics, VaR/CVaR tail risk, covenant-breach probabilities, P50/P90 exceedance energies — and the reverse-engineering solvers that back a target KPI out into a required tariff, debt, or capex.

**Design reasoning:** This is the "core" primitive tier every higher analytics module builds on, so it is deliberately kept thin, contract-typed, and single-responsibility (CCCDIR). It honors ARCH-02 IRR isolation strictly: no module here re-implements IRR/NPV — `metrics.py` and `returns.py` both delegate to the `finance.irr` singleton (R7 compliance), which is the one place IRR/NPV math lives. Outputs are frozen Pydantic V2 contracts (CASPER), and every config surface is fail-fast with no hardcoded defaults (CESSPIT: `ReturnsConfig`/`RiskConfig` require their parameters). Two structural decisions are notable: (1) covenant-breach probability is centralized in a single pure-`numpy` leaf (`covenant_breach.prob_breach`) so a covenant pinned at the dual-DSCR sculpt floor is never mis-reported as a spurious breach; and (2) the exceedance z-score table is a single dependency-free home shared by both wind and solar producers so the two uncertainty build-ups can never silently diverge (DRY/CCCDIR).

### Key modules

| Module | Role |
| --- | --- |
| `metrics.py` | Canonical v14 KPI aggregation engine and single source of truth for scenario-level KPIs. `calculate_scenario_kpis()` / `compute_kpis()` derive CFADS aggregates, DSCR statistics (min/max/mean/median), project NPV/IRR (via `finance.irr`), and lender KPIs (avg_dscr, LLCR, PLCR, equity IRR). Carries careful cleaning rules — a finite DSCR of 0.0 or negative is retained as a real total-coverage breach, only None/inf/nan are dropped — and a percentile helper that uses linear interpolation so its p50 equals the reported median. |
| `returns.py` | Project and equity returns analytics (Pydantic V2, Sprint 15 migration). `calculate_project_returns`, `calculate_equity_returns`, `calculate_npv/irr/mirr`, and `summarize_all_returns` produce `ProjectReturns`/`EquityReturns`/`AllReturns` contracts (IRR, MOIC, DPI, MIRR). Delegates all IRR/NPV to `finance.irr`; `ReturnsConfig` is frozen and config-driven. |
| `risk_metrics.py` | `TailRiskAnalyzer` — the VaR/CVaR/downside-risk engine. Methods: `calculate_var_cvar` (VaR at a confidence level plus CVaR == Expected Shortfall), `percentile_analysis` (P10–P90), `downside_risk` (downside deviation, Sortino ratio, probability-below-target), `covenant_breach_probability` (routes through `covenant_breach.prob_breach`), and `tail_risk_report`/`to_dataframe`. Emits frozen contracts (`VaRCVaRResult`, `DownsideRisk`, `CovenantBreachAnalysis`, `TailRiskReport`). |
| `covenant_breach.py` | Noise-tolerant covenant-breach primitives (single source of truth). `prob_breach(arr, floor)` counts a trial as a breach only when it sits below the floor by more than representation noise (`PROB_BREACH_RTOL = 1e-9`, `np.isclose`-based), fixing a latent bug that fabricated 85–93% breach probabilities on sculpt-floor-pinned DSCR arrays whose true breach probability is 0.0. `is_floor_pinned` lets lender-facing callers disclose that a structural 0.0 carries no distributional signal. |
| `exceedance.py` | Shared exceedance-probability primitives. `EXCEEDANCE_Z` (normal-distribution one-sided z-scores: P50=0, P75=0.6745, P90=1.2816, P95=1.6449, P99=2.3263) and `exceedance_value(p50, sigma_pct, z)` implementing `P_x = P50·(1 − z·σ%/100)`. One table for both wind and solar resource build-ups; a parity test pins both producers to it. |
| `parameter_solvers.py` | Reverse-engineering solvers for derived Monte-Carlo inputs: solve for the tariff that hits a target project/equity IRR or NPV, the max debt satisfying a DSCR (or multi-covenant DSCR+LLCR) floor, the min capex under an IRR floor, and a first-class tariff breakeven surface. Uses bisection, goes through the `evaluate_with_overrides()` gateway only (no direct finance math), and runs `_assert_override_is_live` first so it fails loud rather than bisecting on a no-op override. Dispatched via `SOLVER_REGISTRY`/`get_solver`. |
| `sensitivity_runner.py` | Path-loading entry point for deterministic one-way sensitivity (tornado) analysis. Owns no orchestration of its own — loads a base scenario, builds a default set of empirically-verified LIVE parameter sweeps (CAPEX, OPEX, capacity factor, tariff, corporate tax, debt tenor), and delegates evaluation/contract assembly to `analytics.sensitivity.engine`. |
| `epc_helper.py` | Thin re-export shim exposing `finance.epc_helper_v14`'s `epc_breakdown_from_config`/`epc_breakdown_dict` under the analytics namespace. No logic of its own. |

### Academic / methodological grounding

- `exceedance.py` — IEC 61400-15-2 (wind) and IEC 61724-1 / IEA-PVPS Task 13 (solar): the bankable normal-distribution P50/P75/P90/P95/P99 exceedance z-score convention used to derive lender-facing exceedance energies from a P50 mean and a relative 1-sigma.
- `risk_metrics.py` — Value-at-Risk and Conditional VaR / Expected Shortfall (ES): CVaR is documented in-code as identical to Expected Shortfall (mean of the tail at/below VaR), with an explicit small-sample caveat that ES converges slower than the mean and is noisy at typical trial counts. Also implements the Sortino ratio (mean-minus-target over downside deviation) as the downside-risk statistic. No specific author/paper is cited in-code beyond these named methods.
- All other modules in this domain carry no in-code academic citation; `metrics.py`, `returns.py`, `parameter_solvers.py`, `sensitivity_runner.py`, and `epc_helper.py` are KPI aggregation, contract plumbing, and orchestration/glue.

### Interfaces, optional extras, and limitations

- **Consumes/produces:** inputs are per-scenario config maps, annual cashflow rows, debt results, and Monte-Carlo arrays (IRR/NPV/DSCR/LLCR/PLCR trials); outputs are frozen Pydantic V2 contracts and KPI dicts. IRR/NPV is never computed here — it is delegated to the `finance.irr` singleton (ARCH-02 / R7). Solvers reach the engine only through the `evaluate_with_overrides()` gateway.
- **No optional install extra** powers this domain; it depends only on `numpy`/`pandas`/`pydantic` and the in-repo `finance`/`analytics.contracts_v14` surfaces — there is no CASPER optional-dependency guard here (the guarded extras live in the resource/grid layers, not core primitives).
- **Honesty boundary — covenant breach:** `prob_breach` will report a structural `0.0` when the min-DSCR is pinned at the sculpt floor; that zero carries no distributional signal, and `is_floor_pinned` exists so lender surfaces disclose the degeneracy rather than present it as a risk read.
- **Honesty boundary — tail statistics:** the code itself warns that CVaR/ES is estimated from only `(1−confidence)·n` worst trials (≈10 trials for a 99% ES at n=1000), that a tight mean confidence interval does not certify the tail, and that the `>=20`-sample floor elsewhere is a degeneracy guard, not a sufficiency certificate.
- **Solver limitations (self-disclosed):** the max-debt solvers fail loud under the default `dual_dscr` sizing (the engine sizes debt to the covenant, so "max debt given DSCR" is the solved gearing, not a sweepable absolute); solvers assert an override is LIVE before bisecting; and the module is not yet wired into a Hydra CLI (deferred, issue #615; any exposure must be Hydra-only per GWTF R3/CLI-01). `sensitivity_runner.py` deliberately excludes `Financing_Terms.interest_rate_nominal` from the default tornado because that override is a proven no-op in the current pipeline.

## Monte Carlo Engine

**Path(s):** `analytics/mc/` — `engine.py`, `samplers.py`, `correlation.py`, `convergence.py`, `aggregate.py`, `covenant.py`, `degradation.py`, `exports.py`, `__init__.py`; plus the deprecated shim `analytics/monte_carlo_v14.py` and the standalone AEP sampler `analytics/simulation/monte_carlo_aep.py`.

**Purpose:** Runs the project's probabilistic risk analysis — samples the uncertain financial/technical drivers (capex, tariff, capacity factor, FX, degradation, etc.), re-evaluates the full v14 finance model per trial, and aggregates the trial cloud into lender-grade percentile bands, covenant-breach probabilities, and convergence diagnostics.

**Design reasoning:** The package is the single canonical MC surface for v14; every trial is evaluated through the `analytics.evaluation_v14.evaluate_with_overrides` gateway (ARCH-04/CCCDIR) rather than any private cashflow path, and results are returned only as the `MonteCarloResult` contract from `contracts_v14`. Correlation, degradation, Sobol sampling, and fixed-debt covenant stress are opt-in plug-in steps around one engine class and one entrypoint, not separate engines. The `__init__.py` uses PEP 562 lazy `__getattr__` to break a circular import against `evaluation_v14`, and optional dependencies (SciPy for Sobol, pandas for exports) are guarded at call-time so the module still imports without them (CASPER). Malformed `monte_carlo` config fails loud via `MonteCarloConfigError` (CESSPIT schema-strictness) instead of a cryptic sampler-level `TypeError`.

### Academic / methodological grounding

- `samplers.py` — Latin Hypercube Sampling (stratified one-per-interval design) as the default; Sobol' low-discrepancy quasi-Monte-Carlo (scrambled net, star-discrepancy ~O((log n)^d / n), power-of-two balance contract) as the opt-in alternative, with an in-code caveat citing the 2026-07-02 SOTA link-research digest that the naive "O(1/N)" QMC gloss is overstated.
- `correlation.py` — Iman-Conover rank-correlation reordering (default; documented in-code as approximate Spearman, carrying O(1/√n) score-correlation sampling error) and a Gaussian-copula method with exact normal-scores whitening; both note the latent-scale Spearman distortion `(6/π)·arcsin(ρ/2)` and the honest limitation that a Gaussian copula has zero asymptotic tail dependence for |ρ|<1.
- `convergence.py` — Monte Carlo standard-error mean CI (`z·sd/√k`, cited to the SAS DO-Loop convergence-monitoring note, Welford-equivalent); binomial order-statistic percentile CI (Conover, *Practical Nonparametric Statistics*; Hahn & Meeker, *Statistical Intervals*) with normal approximation to the ranks; Wilson score interval for breach proportions.
- `monte_carlo_aep.py` — cites IEC 61400-15-1:2025 (site-specific wind conditions), NREL TP-500-38977 (wind energy uncertainty), and DFI bankability guidelines.
- `engine.py`, `aggregate.py`, `covenant.py`, `degradation.py`, `exports.py` — no formal academic grounding; orchestration, contract plumbing, and config-first covenant/export logic.

### Interfaces, optional extras, and limitations

- **Consumes:** a plain (OmegaConf-deconverted) `monte_carlo` config block (parameters, bounds, sampler, correlation, degradation, fixed_debt_stress, allow_toy_fallback) plus the base v14 config; **produces:** a `MonteCarloResult` contract carrying raw per-trial arrays, percentile bands, and a metadata bag (`run_meta`, `convergence`, `percentile_ci`, `correlation_enabled`, `degenerate_sweep`, `zero_variance_metrics`, and, for Sobol, `sobol_n_requested` vs used n).
- **Optional extras:** SciPy powers the opt-in Sobol QMC sampler (`scipy.stats.qmc`, imported lazily; a missing install raises a directed error rather than failing at import); pandas powers the lender-table exports (guarded import). LHS + Iman-Conover run on numpy alone.
- **Default-off / opt-in levers disclosed in code:** `sampler: sobol`, `correlation.enabled` (+ `method: gaussian_copula`), `degradation.enabled`, and `fixed_debt_stress` are all opt-in and byte-identical to the historical single-path run when unset; the Gaussian copula additionally requires `n_trials > n_params` (fails loud otherwise).
- **Honesty boundaries the code itself states:** Sobol buys little on DutchBay's non-smooth binding KPIs (min_dscr clamped at the covenant floor, equity_irr kinked at debt sizing) and is never the silent default; combining Sobol with correlation destroys the joint low-discrepancy structure (marginals survive) and emits a one-time warning. The convergence mean CI bounds only the mean and does not certify the tails a lender reads; the order-statistic tail CI is distribution-free but still approximate on an LHS/Iman-Conover design (a prefix of an LHS design is not itself LHS), and reports a bound as `None` (loud omission) when n is too small to place the rank rather than clamping to an extreme order statistic.
- **Toy fallback caveat:** on a real run, a per-trial toy-metric substitute means full v14 evaluation failed for that trial; the KPIs are fabricated (though tagged and counted in `toy_fallback_count`). `monte_carlo.allow_toy_fallback: false` makes a production run raise on the first failed trial instead of reporting fabricated numbers.

## Global Sensitivity & Optimization

**Path(s):** `analytics/sensitivity/` — `engine.py`, `global_sa.py`, `interaction.py`, `tail_risk.py`, `optimizer.py`, `dscr.py`, `tax.py`, `adapters.py`, `export.py`, `validation.py`, `__init__.py`; plus `analytics/sensitivity_v14.py`, `analytics/dscr_sensitivity.py`, `analytics/wacc_sensitivity.py`.
**Purpose:** Quantifies how project KPIs (project/equity IRR, min DSCR, NPV) respond to driver movements — from local one-at-a-time tornado sweeps through variance-based and moment-independent global decomposition to multi-objective Pareto/NSGA-II trade-off search — producing read-only, lender-facing analysis artifacts that never touch the deterministic base case.
**Design reasoning:** The package sits downstream of the finance engine and evaluates every scenario exclusively through the `analytics.evaluation_v14.evaluate_with_overrides()` gateway (ARCH-04), so it holds no IRR/NPV math of its own (ARCH-02) and reuses the SAME `monte_carlo.parameters` driver list the MC engine reads (CESSPIT config-first — no new authored constants). Result types live in `contracts_v14` and are reached via a single `adapters.py` conversion layer (CCCDIR — one contract surface). Heavy optional backends (SALib, pymoo) are guarded by call-time `_require_*()` gates so the base finance install never needs them (CASPER), and the package `__init__.py` uses lazy `__getattr__` loading to avoid a circular import with `evaluation_v14`. The whole domain is explicitly additive and KPI-neutral: it emits new artifacts only and never mutates the base case.

**Path(s):** `analytics/wind/` (pipeline_aep_v14.py, wind_integration.py, mc_aep_weibull.py, losses_model.py, aep_tornado.py, wind_rose.py, aep_summary_builder.py, siting_metadata.py, era5_interface_schema.py, wind_interface_schema.py, crossval_interface_schema.py); `analytics/gis/` (geotiff_export.py, gwa_ingest.py, dem_ingest.py, landcover_roughness.py, boundary_clip.py, exclusion_mask.py, rix.py, mcdm_suitability.py); `analytics/loader/aep_loader.py`; `analytics/power_curves/oem_parser.py`.

**Purpose:** Converts a site's wind resource into a bankable net-AEP figure — power-curve energy integration, an explicit gross→net loss stack, Monte-Carlo and tornado uncertainty, and provenance — then normalises it into the `resource.wind`/`aep` contract the finance engine consumes; the GIS half produces the terrain, land-cover, exclusion and multi-criteria siting rasters that underpin turbine micro-siting.

**Design reasoning:** This domain is the boundary between the wind-resource science (the `wind_resource/` package) and the v14 finance model: `analytics.wind` re-implements the AEP math method-consistently with `wind_resource` while depending only on the certified power-curve store and config, keeping analytics decoupled from that package. It is strictly config-first (ARCH-01 — no hardcoded curves, losses, or turbine counts), routes every AEP source through an approved-source manifest with checksum/IEC provenance (CESSPIT schema-strictness via `RequiredFieldSpec`/`validate_config_for_v14`), and CASPER-guards the heavy GIS toolchain (`rasterio`/`shapely`) behind the optional `[gis]` extra so the base finance install never needs GDAL. A deliberate honesty boundary runs through the whole domain: every GIS/rose/siting layer is documented as KPI-neutral and default-off, never silently scaling the committed AEP oracle.

| Module | Role |
| --- | --- |

| `losses_model.py` | Explicit multiplicative gross→net loss stack. | `aep_loader.py` | Loads pre-computed AEP summaries from the Data Lake with SHA-256 checksum verification and validation against `APPROVED_SOURCES` (the manifest carrying type, IEC standard, certificate and `curve_key` per source); `register_approved_source` allows config-driven extension without weakening provenance. |

### Academic / methodological grounding

- `oem_parser.py` — IEC 61400-12-1:2022 (power-performance measurement; reference air density 1.225 kg/m³ and the site air-density correction); SciPy PCHIP / CubicSpline for curve interpolation.
- `aep_tornado.py` — IEC 61400-12-1 velocity-cube air-density correction `(ρ_site/ρ_ref)**(1/3)` applied as a wind-speed-axis shift; analytic Weibull integral with linear power-curve interpolation (method-consistent with `wind_resource.EnergyCalculator`).
- `losses_model.py` — IEC 61400-15-2-aligned loss taxonomy (turbine performance, high-wind hysteresis, icing, transmission, soiling, blade degradation, availability/grid uptime).
- `mc_aep_weibull.py` — Justus (1978) method-of-moments Weibull fit; ECMWF ERA5 hub-height (ws150) series as the resource source; wind-industry exceedance convention (P90 = 10th percentile).
- `aep_summary_builder.py` — IEC 61400-15-2 uncertainty budget (`UncertaintyBudget`, `budget_from_mapping`, `exceedance_levels`, recommended P50 haircut) via `wind_resource.bankable_aep`; IEC 61400-12-1 density correction.
- `aep_loader.py` — IEC standard registry (61400-12-1:2022 power performance; 61400-15-1:2025 site conditions; 61400-21:2008 power quality) recorded in source provenance.
- `dem_ingest.py` — Horn's (1981) 3×3 slope/aspect kernel (the math `gdaldem` uses); Copernicus GLO-30 primary DEM, SRTM 1-arcsec fallback.
- `landcover_roughness.py` — WMO / Davenport–Wieringa roughness classification (Wieringa 1992, *J. Wind Eng. Ind. Aerodyn.* 41; WMO-No. 8 CIMO Guide) reclassified for ESA WorldCover ~10 m per the Global Wind Atlas v3/v4 pipeline (Davis et al., 2023, *Global Wind Atlas v3*, DTU); notes CORINE-based tables (Silva et al., 2007) as a Europe-only 100 m schema reference only.
- `gwa_ingest.py` — Global Wind Atlas 250 m (DTU), ERA5→WRF 3 km→DTU generalization→WAsP microscale chain; native resolution per Davis et al., BAMS 2023.
- `rix.py` — RIX/ΔRIX per Mortensen, Bowen & Antoniou (2006, DTU/Risø): WAsP prediction error is log-linear in ΔRIX, with |ΔRIX| > ~5% as the terrain-correction threshold; conventional critical slope 0.3 (≈16.7°).
- `mcdm_suitability.py` — Saaty (1980, 2008) Analytic Hierarchy Process (principal-eigenvector priority via normalised-column mean; `CI=(λmax−n)/(n−1)`, `CR=CI/RI(n)`, Saaty Random Index table, CR ≤ 0.10 acceptance); Boolean-constraint-then-weighted-scoring wind-farm-siting recipe per Cunden et al. (2020, *Energy* 205:118533, Mauritius wind-farm siting).
- `wind_rose.py`, `siting_metadata.py`, `boundary_clip.py`, `exclusion_mask.py`, `geotiff_export.py`, `pipeline_aep_v14.py`, `wind_integration.py`, the three interface schemas — no formal academic grounding; orchestration, GIS geometry plumbing, and contract registration (schema/provenance discipline rather than a cited method).

### Interfaces, optional extras, and limitations

- **Consumes:** scenario config (`resource.power_curve` curve/source identifiers, `resource.losses`, `resource.turbines`, `resource.era5`, optional `resource.crossval`/`resource.siting`), the shared `power_curves.yaml` store, approved AEP-summary JSON (checksum-verified), and locally-supplied GeoTIFFs (GWA, GLO-30 DEM, ESA WorldCover). **Produces:** the normalized `resource.wind`/`aep` block feeding revenue, MC percentile + tornado CSVs, an AEP summary JSON with IEC-graded provenance, and provenance-stamped GIS rasters plus Data-Lake manifest entries.
- **Optional extra:** all GIS raster I/O (geotiff_export, gwa_ingest, dem_ingest, landcover_roughness, boundary_clip, exclusion_mask, and rix's optional export) requires the `[gis]` install (`rasterio`, `shapely`); it is CASPER-guarded at call time so the base finance install runs without GDAL. The pure-numpy math (RIX point/array, AHP/WLC, loss retention) needs no extra and is independently testable.
- **Honesty boundaries the code itself discloses:** the wind rose is single-grid-cell ERA5 reanalysis (~0.25°), labelled coarse and not mast-validated; GWA layers are reference/visualization only and explicitly NOT wired into the AEP/KPI path; siting metadata applies no AEP correction; the entire GIS/siting stack is KPI-neutral and add-only, leaving the committed AEP oracle unchanged.
- **Default-off levers:** `resource.crossval` second-source cross-validation is opt-in (default off, byte-identical when absent); Monte-Carlo AEP runs only when `monte_carlo.enabled`; the air-density correction defaults to none unless both density fields are present; the tornado power-curve driver is skipped unless the scenario names a comparable `alt_curve_key`.
- **Documented modelling caveats:** the shared `gross_aep_farm_gwh` handles cut-out implicitly via `np.interp(..., right=0.0)` (the supplied curve must already encode cut-out) and agrees with `wind_resource.bankable_aep.gross_aep_weibull` to <0.1% on the canonical IEA-10MW curve — a bounded, disclosed style difference, not bit-identical; the `mc_aep_weibull` docstring's ~402.6 GWh EN-171/6.5 figures are legacy and regenerate from their own config, while the live lender basis is 15×IEA-10MW (net ≈473.8 GWh, CF 0.339, ERA5 Weibull A≈8.199/k≈2.665; frozen `aep_summary_dutchbay_10mw.json` headline 464.3 GWh).

## Grid interconnection screening study

**Path(s):** `analytics/grid/` — `evaluate_grid.py`, `short_circuit.py`, `ride_through.py`, `ride_through_poc.py`, `curtailment_qsts.py`, `reactive_screen.py`, `frequency_response.py`, `harmonics.py`, `grid_interface_schema.py` (plus the `capabilities/` per-technology and `hybrid/` POC-aggregation sub-packages).

**Purpose:** A design-stage electrical screening layer that estimates point-of-connection (POC) grid strength (SCR), reactive/voltage capability, fault ride-through, frequency-response de-load cost, harmonic/flicker power quality, and QSTS curtailment for the plant. It is explicitly advisory only — it never feeds the finance engine, so committed scenarios stay byte-identical.

**Design reasoning:** The package exists to give the model an in-house, pre-consultant read on interconnection feasibility (chiefly the grid-following vs grid-forming inverter decision at the POC) without licensing PSS/E or PowerFactory. It is deliberately additive and default-off: nothing here is imported by `finance.*` or `analytics.pipeline_*`, gated behind `grid.study_enabled`, so it is KPI-neutral (ARCH IRR-isolation is respected by construction — no IRR/NPV logic here). Analytics consumers reach the engine only through the `evaluate_grid` gateway and consume result types only from `analytics.contracts_v14` (CCCDIR). Every heavy library (`pandapower`, `andes`, `opendssdirect`) is an optional `[grid]` extra guarded at call-time by `_require_*()` helpers, never imported at module load (CASPER), so a grid-free install imports the package cleanly and falls back to closed-form paths. Config is strict-validated when a `grid` block is present (CESSPIT), with no silent defaults for FX/fault-level/thevenin inputs.

### Key modules

| Module | Role |
| --- | --- |
| `evaluate_grid.py` | The CCCDIR gateway — the single typed entry point (analogue of `evaluate_with_overrides` for finance). Composes the SCR strength screen and the steady-state reactive screen into one `GridStudyResult` (all `bankable=False`); raises rather than silently no-op'ing when `grid.study_enabled` is not True. |
| `short_circuit.py` | SCR@POC grid-strength screen — the pivotal GFL-vs-GFM decision. Builds a `source → connection → POC` network in pandapower and computes the POC fault level via IEC 60909 (both MIN and MAX cases; the weakest MIN case governs bankability), bands the SCR, and flags the EMT-confirmation threshold. Closed-form Thevenin fallback when pandapower is absent (`method="closed_form"`). |
| `ride_through.py` | Shared ANDES RMS ride-through core. Runs one parameterised LVRT (voltage dip / shunt fault), HVRT (over-voltage swell via load rejection), or frequency (generator trip / load step) case against a generic WECC IBR, seeded from the redacted D0 grid-code fixture. Crucially separates solver convergence from the physical-envelope compliance verdict (`rode_through`); gated behind `run_dynamics` (default False) so the default path stays static and never imports andes. |
| `ride_through_poc.py` | Backward-compatibility SHIM (deprecated). `run_lvrt_case` delegates to the `ride_through.py` core's `"lvrt"` case and adapts it back to the legacy `LvrtScaffoldResult` shape; `ran` means the solve executed, not that it passed. |
| `reactive_screen.py` | Steady-state reactive/voltage PQ-box screen. Builds an `ext_grid → POC transformer → collector → resources` network and runs a pandapower AC load-flow over a P × grid-voltage sweep, commanding each converter to its Q-limit, then measures any Mvar shortfall against the grid-code PQ box at the worst operating point. |
| `harmonics.py` | SCR-coupled harmonics/flicker power-quality screen. Estimates POC harmonic voltage (`V_h = |Zbus(h)|·I_h`, impedance referred to Ssc, or a pandapower frequency-domain Zbus scan when `[grid]` is present) vs IEEE 519:2022 voltage limits, indexes the current-TDD limit by Isc/IL, and computes IEC 61400-21 flicker Pst — all degrading as SCR falls. |
| `frequency_response.py` | Pure-Python frequency-response de-load sizing. Closed-form (droop × band × capacity-factor) MW headroom the plant reserves for primary-frequency response and the annual MWh/yr foregone — the de-load opportunity cost. No grid library. |
| `curtailment_qsts.py` | OpenDSSDirect QSTS curtailment engine. Runs a quasi-static time-series power flow over a real feeder, splits curtailed energy into deemed-paid/grid-instructed (explicit input, KPI-neutral under the CEB SPPA) vs self-curtailed above the export cap (the real energy loss), with energy-conserved BESS charge-from-surplus absorption. Refuses to emit a real figure for a synthetic/demo feeder. |
| `grid_interface_schema.py` | CESSPIT config contract for the top-level `grid` block. Registers strict required-field specs (D1 flat screen inputs + D2 structured `poc`/`thevenin`/`scr`/`gridcode`/per-tech blocks), enforced only when a `grid` block is present; `study_enabled` is a strict required bool with no silent default. |
| `capabilities/`, `hybrid/` | Per-technology grid-capability plug-ins (wind/solar/bess, plus the D5a BESS SoC reserve-split model) keyed on `finance.tech_types`, and static hybrid-POC aggregation summing each tech onto one POC bus into a `PocCapabilityEnvelope`. |

### Academic / methodological grounding

- `short_circuit.py` — IEC 60909 (short-circuit fault-level calculation via `pandapower.shortcircuit.calc_sc`, MIN and MAX cases; `endtemp_degree=80 °C` R-temperature correction for the min-case lower bound). SCR-banding into the GFL/GFM viability and EMT-confirmation decision.
- `ride_through.py` / `ride_through_poc.py` — WECC generic renewable-energy IBR models (REGCA1 / REGCP1 / REECA1 / REPCA1, with Type-3 wind / PVD1 / GENROU fallbacks) solved in ANDES RMS positive-sequence time-domain simulation; envelope thresholds parameterised from the OEM D0 grid-code fixture.
- `harmonics.py` — IEEE 519:2022 (Table 1 voltage-distortion limits by kV band; Table 2 total-demand-distortion current limits indexed by Isc/IL), IEC 61400-21 (short-term flicker Pst = c(ψk,va)·S_rated/Ssc), and IEC 61000-3-7 (0.35 HV/EHV flicker planning limit).
- `reactive_screen.py` — pandapower AC load-flow (`runpp`) over the P × grid-voltage envelope; PQ-box / power-factor sizing (`Q = P·tan(acos(pf))`). Method (load-flow) rather than a named external standard; Q-limits from the OEM reactive-capability curve.
- `curtailment_qsts.py` — OpenDSSDirect quasi-static time-series (QSTS) power flow; the deemed-vs-self curtailment split follows the CEB standardised PPA deemed-energy treatment (a commercial convention, not an academic standard).
- `frequency_response.py`, `grid_interface_schema.py`, `evaluate_grid.py` — no formal academic grounding; closed-form droop sizing on conventional grid-code values, schema/contract plumbing, and orchestration respectively.

### Interfaces, optional extras, and limitations

- **Consumes:** the scenario config `grid` block (flat D1 screen scalars — `poc_voltage_kv`, `source_fault_level_mva`, `source_rx`, `connection_r/x_ohm`, `plant_rating_mva` — plus the D2 structured `poc`/`thevenin`/`scr`/`gridcode`/per-tech sub-blocks) and the redacted D0 grid-code fixture (`tests/fixtures/grid/envision_enpcs01_gridcode.yaml`). **Produces:** advisory `analytics.contracts_v14` result types — `GridStudyResult`, `GridStrengthResult`, `ReactiveCapabilityResult`/`PowerFlowResult`, `RideThroughResult`, `HarmonicComplianceResult`, `CurtailmentShareResult`, `PocCapabilityEnvelope` — all carrying `bankable=False`.
- **Opt-in extra:** the `[grid]` install (`pandapower>=3.3,<3.4`, `andes`, `opendssdirect`) powers the IEC 60909 fault calc, ANDES dynamics, and QSTS. Absent, the SCR/reactive/harmonics screens fall back to closed-form (`method="closed_form"`) and the dynamics/QSTS paths return honest NOT-RUN results.
- **Honesty boundary (stated in every module docstring and stamped in each result's provenance):** this is design-stage SCREENING only, not the utility-accepted bankable connection study. CEB/NSCC require PSS/E or PowerFactory against their confidential grid base case, and a true FRT/harmonic compliance study is an EMT (PSCAD/EMTP) run with the OEM `.dyr`/`.dll`/`.pfd` binaries — which feed that study, not this one.
- **Convergence is not compliance:** `ride_through.py` never reads an ANDES convergence flag as a pass; the `rode_through` verdict comes only from the measured post-disturbance voltage/frequency vs the envelope and IBR-trip status, with `None` reserved for genuinely not-exercised cases (no fabricated pass).
- **Default-off levers:** the whole study is gated by `grid.study_enabled`; the ANDES dynamics path is additionally gated by `run_dynamics` (default False); QSTS is gated by `grid.qsts.enabled` and refuses to emit a real curtailment figure for a synthetic/demo feeder. Self-curtailment is the sole future KPI-mover but is wired to finance only by a separate downstream dolphin (D6b), not by this package.

## Cost Engine, Portfolio & Bankability Register

**Path(s):** `analytics/cost/` (`cost_basis.py`, `estimate_class.py`, `contingency.py`, `mc_capex.py`, `benchmark.py`); `analytics/portfolio/` (`generation_aggregator.py`, `tech_wbs.py`, `multi_tech_tornado.py`, `poi_curtailment.py`); the lender/bankability register `analytics/aep_provenance.py`, `aep_reconciliation.py`, `evidence_register.py`, `evidence_score.py`, `conditions_precedent.py`, `development_readiness.py`, `feasibility_sections.py`, `infeasibility_diagnostics.py`; and the reporting/workbook layer `analytics/executive_workbook.py`, `reproducible_workbook.py`, `three_statement.py`, `irr_bridge.py`, `export_helpers.py`, `output_paths.py`.

**Purpose:** Anchors and stress-tests the CAPEX/OPEX cost stack on recognized cost-estimating standards, splits a real finance run into per-technology generation/cost/return views for hybrid plants, and maintains the lender/DFI provenance-and-readiness registers (AEP source, assumption evidence, conditions precedent, development readiness) plus the board-facing workbook, three-statement and IRR-bridge outputs. It is the disclosure and bankability layer around the finance engine.

**Design reasoning:** These modules are deliberately additive and KPI-neutral: none recomputes economics, all IRR/NPV math is delegated to `finance/irr.py` (ARCH-02 / R7 singleton) and every result type is centralized in `analytics.contracts_v14` (ARCH-04 / CCCDIR gateway). Cost anchors, AACE bands, benchmark ranges and register taxonomies are config-first — sourced from `config/defaults.yaml` and dedicated `config/*.yaml` files, never Python literals (CESSPIT schema-strictness). The provenance/reconciliation modules are pure detectors that raise-or-no-op at authored-scenario load time, so they preserve byte-identical economics while making a stale or unevidenced assumption fail loud; the registers are soft-by-default (warn, render-when-present) so lender-grade scenarios opt into hard enforcement rather than breaking simplified base cases.

### Interfaces, optional extras, and limitations

- **Consumes/produces:** the cost engine consumes `capex.*` scenario config plus `config/defaults.yaml → defaults.cost_reference` anchors, producing `ContingencyResult`, `CapexMcResult`, and benchmark/estimate-class dicts; `mc_capex` re-invokes the full v14 pipeline per draw. The portfolio and bankability layers consume a completed run's contracts (`analytics.contracts_v14`) plus per-scenario declaration blocks and their `config/*.yaml` taxonomies, producing generation/WBS/tornado/curtailment views and register rollups; the reporting layer emits `.xlsx` workbooks, three-statement frames and the IRR bridge.
- **Optional extras / graceful degradation:** the bankable net-AEP P50/P90 export that `aep_reconciliation.py` and `aep_provenance.py` reconcile against is produced by the opt-in `[wind]` extra (cdsapi / xarray / windpowerlib / PyWake); absent a bankable reference these guards simply skip (no false failure). Excel emitters guard openpyxl/matplotlib imports defensively (CASPER — optional deps fail at call time, not import time).
- **Report-only / disclosure-only boundaries:** `benchmark.py` never raises or changes a value (out-of-band is a flag/log only); per-tech `capex_usd` is reporting-only (the "phantom-capex" decoupling — financed CAPEX is `capex.usd_total`); `tech_wbs.py` per-tech WACC and `poi_curtailment.py` (against a frozen AEP) are disclosed-only and never silently move committed economics.
- **Soft-by-default registers:** `evidence_register`, `evidence_score`, `conditions_precedent`, `development_readiness`, `feasibility_sections` default to `enforce: false` / `require_complete: false` (warn or report, never break); lender/IC-grade scenarios must explicitly opt into hard enforcement (e.g. `require_complete: true`, `min_tier: benchmark`).
- **Honesty caveats disclosed in-code:** `aep_reconciliation` is a detector, not a single-source-of-truth fix — `capacity_mw × CF` remains the billed quantity and a stale capacity with no bankable reference still passes; widening its tolerance is an audited (WARNING-logged) override. `mc_capex` uses a fixed straight-percentile convention (for CAPEX p90 is adverse; for IRR/NPV/min-DSCR p10 is adverse). `irr_bridge` retains an explicit residual because IRR is non-additive; `three_statement` articulation invariants are builder guards, with `debt_retires_to_residual` the one independent tie-out. Run-scoped output paths and reproducible-workbook normalization are default-off / last-step so committed runs stay byte-identical.

## Finance engine (deterministic cashflow, debt, tax, returns)

**Path(s):** `finance/` — `irr.py`, `irr_config.py`, `wacc_v14.py`, `cashflow_v14.py` and its split helpers (`cashflow_v14_production.py`, `_tax.py`, `_fx.py`, `_params.py`, `_contracts.py`, `_utils.py`), `debt_v14.py`, `equity_v14.py`, `equity_distribution_v14_hydra.py`, `tech_types.py`, `self_curtailment_v14.py`, `import_levies.py`, `epc_margin.py`, `epc_helper_v14.py`, `bess_revenue.py`, `bess_lcos.py`, `bess_project_economics.py`, `utils.py`, `finance/grid/grid_types.py`.

**Purpose:** The deterministic core of the model: it converts a validated YAML scenario into the project's annual CFADS (revenue, opex, statutory deductions, tax), sizes and services debt against DSCR/LLCR/PLCR covenants, resolves the equity waterfall, and computes the headline project/equity IRR, NPV and WACC. Every committed KPI (projIRR, eqIRR, NPV, gearing, min_DSCR) originates here.

**Design reasoning:** IRR/NPV live in exactly one place (`finance/irr.py`, ARCH-02 / R7 single source of truth) and every other module — equity, EPC margin, BESS economics — delegates to it rather than re-implementing a solver. Result types flow through the `analytics.contracts_v14` gateway (CCCDIR: e.g. `WaccComponents`, `EquityPerformance`), and config resolution is fail-loud (CESSPIT: `as_float` raises on a malformed-but-present value rather than silently defaulting a tax or capex base). The large `cashflow_v14.py` was decomposed into single-responsibility helpers (production / tax / fx / params / contracts) as a Dolphin-strategy refactor while preserving `build_annual_rows` as the stable public feedstock for `debt_v14.plan_debt` and the contracts layer. New economic seams (FX hedging, self-curtailment, BESS, import levies) are added default-off so the committed canon stays byte-identical unless an explicit opt-in switch is set.

### Academic / methodological grounding

- `wacc_v14.py` — CAPM (Ke = Rf + β·MRP) for cost of equity, textbook asset-beta re-levering `β_equity = β_asset·[1+(1−T)·(D/E)]`, and the Fisher relationship for nominal→real WACC conversion.
- `cashflow_v14_production.py` — IEC 61400-12-1:2022 (Annex C, performance monitoring) for turbine performance degradation; Staffell & Green (2014) for wind-farm degradation analysis; NREL (2019) long-term performance trends.
- `cashflow_v14_fx.py` / `cashflow_v14_contracts.py` — Covered Interest Parity (CIP) forward, `forward_t = spot_0·((1+r_lkr)/(1+r_usd))^t`, as the hedge/forward FX basis.
- `bess_revenue.py`, `bess_lcos.py` — NREL BLAST (Battery Lifetime Analysis and Simulation Tool; Smith et al., NREL — the lifetime model behind SAM's battery module) for the separable calendar+cycle aging decomposition; NREL ATB 2024/2023–24 for the canonical round-trip-efficiency baseline (0.85).
- `bess_lcos.py` — LCOE-analogue LCOS methodology (`PV(lifetime cost)/PV(lifetime discharged energy)` at WACC), with the fixed-`cycles_per_year` simplification explicitly contrasted against 2025–26 MILP/stochastic dispatch-optimisation LCOS.
- `debt_v14.py`, `equity_distribution_v14_hydra.py`, `import_levies.py`, `cashflow_v14_tax.py` — no formal academic paper cited in-code; these encode project-finance covenant conventions (DSCR-sculpting, LLCR/PLCR) and the Sri Lanka statutory regime (Inland Revenue Act, BOI s.17, Act 24/2025, CEB standardised PPA) as regulatory/contractual references rather than academic ones.

### Interfaces, optional extras, and limitations

- **Consumes:** a single validated YAML scenario dict (through `validate_config_for_v14` / CESSPIT). **Produces:** annual CFADS rows, a debt result (schedule + DSCR/LLCR/PLCR series), an equity distribution waterfall, and the headline KPI set (projIRR, eqIRR, NPV, gearing, financed capex, min_DSCR), surfaced via the `contracts_v14` dataclasses.
- **Default-off / KPI-neutral levers the code itself discloses:** the CIP FX hedge (`hedge_ratio 0.0` ⇒ pure-spot, byte-identical), `import_levies` (`taxes_indirect` absent ⇒ all lines zero), `self_curtailment_v14` (requires `grid.qsts.finance_wiring.enabled`), and the entire BESS-LCOS / standalone-BESS-economics path (read-only, off the committed cashflow). This is the one canon-mover currently user-gated.
- **Debt honesty boundary:** a fixed-tenor sculpted schedule need not fully amortise; the residual balloon must be resolved by the equity waterfall (cash_sweep default) or equity IRR is overstated — `legacy_ignore` is retained only to reproduce the pre-fix (incorrect) numbers.
- **Tax scope:** VAT is intentionally excluded as a cashflow-neutral pass-through for a BOO IPP; only genuine construction-phase VAT timing is out of scope, and this is documented rather than silently dropped.
- **BESS limitations (stated for lender DD):** dispatch is not simulated/optimised (fixed `cycles_per_year`); LCOS opex attribution is clean only for a standalone battery, and on a hybrid it is excluded (understating cost) unless the BESS block declares its own opex — each case carries an in-result note. No third-party install extra powers this domain; it is pure-Python (`numpy_financial`, `pyyaml`, `pydantic`), with the grid/QSTS `[grid]` extra relevant only to the upstream study that feeds the default-off self-curtailment seam.

## Wind Resource Pipeline (ERA5 to bankable AEP)

**Path(s):** `wind_resource/` — `wind_pipeline.py`, `arco_assessment.py`, `bankable_aep.py`, `weibull_fit.py`, `wind_analyzer.py`, `energy_calculator.py`, `mcp.py`, `long_term_trend.py`, `crossval.py`, `layout_optimizer.py`, `era5_fetcher.py`, `era5_retrieval.py`, `era5_grid.py`, `power_curve_sourcing.py`, `cashflow_adapter.py` (config in `wind_resource/config/`).

**Purpose:** Converts ERA5 reanalysis wind data into a standards-referenced, lender-grade Annual Energy Production (AEP) estimate — from data retrieval and hub-height extrapolation, through Weibull characterisation, wake modelling and an IEC uncertainty build-up, to the P50/P75/P90 capacity factor that feeds the finance model.

**Design reasoning:** The domain is split into a live diagnostic/timeseries pipeline (`WindPipeline` → `era5_*` → `WindAnalyzer` → `EnergyCalculator`) and a separate canonical analytic-Weibull engine (`bankable_aep.py`, consumed by `analytics.wind.aep_summary_builder`) that produces the frozen bankable headline; the two are deliberately reconciled (shared `HOURS_PER_YEAR = 8760`, shared IEC density/exceedance math) so the diagnostic path can never silently move committed economics. It is config-first (GWTF ARCH-01 — no hardcoded site or turbine constants; identity fields raise rather than default, honoring CESSPIT schema-strictness) and no finance logic (IRR/NPV) lives here. Heavy geoscience dependencies (`cdsapi`, `xarray`, `py_wake`, `topfarm`, `windpowerlib`) are all call-time guarded (CASPER optional-dep pattern) behind opt-in install extras, so the base install and CI import the modules cleanly and exercise the pure math on synthetic/injected series with no network. Second-source and on-site-mast corrections (MCP, cross-validation, ARCO fit, long-term trend) all run in an explicit VALIDATE / disclose-don't-mutate mode: they surface drift against the declared baseline but never overwrite the frozen resource except at a dated, authorized re-baseline.

### Key modules

| Module | Role |
| --- | --- |

### Academic / methodological grounding

- `bankable_aep.py` — IEC 61400-12-1 (air-density wind-speed normalization, `v_corr = v·(rho_site/rho_ref)^(1/3)`, applied to a reference-density power curve); Bastankhah & Porte-Agel 2014 Gaussian wake deficit via PyWake (DTU), with a `turbopark` conservative alternative; Niayifar & Porte-Agel 2016 turbulence-intensity closure `k* = 0.38·TI + 0.004` for wake growth; IEC 61400-15-2 (P50/P75/P90 uncertainty build-up — seven category sigmas combined by root-sum-of-squares in quadrature, interannual variability separated for 1-year vs project-life P90).
- `energy_calculator.py` — IEC 61400-12-1 (density velocity correction) and IEC 61400-15-2 (exceedance/P-level build-up), reusing `bankable_aep` helpers and the shared `analytics.core.exceedance` z-score table.
- `weibull_fit.py` / `wind_analyzer.py` — 2-parameter Weibull maximum-likelihood estimation via `scipy.stats.weibull_min` with `floc=0`; energy goodness-of-fit expressed as E[v³] relative error (high-wind-tail-sensitive).
- `mcp.py` — Measure-Correlate-Predict per IEC 61400-15-2 / MEASNET practice; variance-ratio vs OLS transfer methods; sample-count bankability thresholds cite Sheridan et al., Wind Energy Science (2025) (long-term capacity-factor errors of ~47%/26%/16% for 1/3/6-month campaigns), with a fully bankable campaign ≥ ~12 months per IEC 61400-15-2.
- `long_term_trend.py` — Mann-Kendall trend test + Sen's-slope / Theil-Sen estimator (with OLS R² for regime-shift-vs-stilling classification); minimum-record and reference-period guidance per IEC 61400-15-1 / MEASNET.
- `layout_optimizer.py` — DTU TopFarm gradient (AEP-maximising) layout optimizer built on PyWake, using the same Bastankhah–Porte-Agel 2014 Gaussian model and Niayifar & Porte-Agel `k*` closure as the bankable engine so scored candidates reconcile.
- `era5_fetcher.py` / `era5_retrieval.py` — power-law (shear-exponent) hub-height extrapolation; `era5_retrieval` derives per-hour α from the ws100/ws10 log profile, with a 1/7-power-law (α = 0.143) coastal/neutral-stability fallback.
- `power_curve_sourcing.py` — Open Energy Database (oedb) open turbine library via `windpowerlib` for the fetch path.
- `wind_pipeline.py`, `era5_grid.py`, `arco_assessment.py`, `crossval.py`, `cashflow_adapter.py` — no independent formal academic grounding; orchestration, GIS assembly, contract plumbing and disclosure wiring around the methods above.

### Interfaces, optional extras, and limitations

- **Consumes:** a Copernicus CDS key in `~/.cdsapirc` plus a project centre (lat/lon) and turbine identity from scenario YAML; power curves from `wind_resource/config/power_curves.yaml`. **Produces:** hub-height wind timeseries, fitted Weibull `(A, k)`, gross/net AEP, P50/P75/P90 capacity factors, GIS rasters, and a JSON export the `cashflow_adapter` maps into a v14 finance scenario (writing to `project.capacity_factor`).
- **Opt-in extras:** `[wind]` powers ERA5 retrieval and PyWake wake modelling (`cdsapi`, `xarray`, `netcdf4`, `py_wake`); `[micrositing]` powers TopFarm layout optimization; `windpowerlib` (lazy) powers the oedb power-curve fetch; MERRA-2 cross-validation uses the base `requests` dependency against the no-auth NASA POWER endpoint. Each is CASPER call-time guarded (`_require_pywake`, `_require_topfarm`, etc.) so absence yields an actionable error naming the extra, not an import failure.
- **Two AEP paths, one headline:** the analytic-Weibull `bankable_aep` engine (via `analytics.wind.aep_summary_builder`) produces the frozen, auditable net-P50 headline; the `EnergyCalculator` timeseries path is a diagnostic and is not on the finance path. The code enforces `HOURS_PER_YEAR = 8760` on both to keep them reconciled (a prior 8766 mean-Julian value caused ~0.07% cross-engine drift).
- **Disclose-don't-mutate honesty boundary:** MCP, `crossval`, `arco_assessment`, `weibull_fit` and `long_term_trend` are default-off / VALIDATE-mode — they surface resource drift against the declared baseline but never silently move committed economics; adopting a fitted `(A, k)` or a corrected resource is a deliberate, dated, authorized config re-baseline. Committed scenarios that do not enable these blocks stay byte-identical.
- **Disclosed caveats:** `era5_grid` fine-resolution fields are a bilinear downscale of 0.25° reanalysis, explicitly labelled as interpolation rather than measured sub-grid observation; MCP flags fits below ~4 months of concurrent data as statistically fittable but not bankable (and ≥12 months for full seasonality); NEWA is a documented EU-coverage-only cross-validation label that is never fetched for the Sri Lanka site; `long_term_trend` degrades explicitly below 10 distinct calendar years rather than emitting a spurious trend statistic. Cross-validation deliberately uses only no-auth/no-cost endpoints — the code states that any move to a credentialed or paid data source must stop and ask the user first.

## Solar Resource Producer

**Path(s):** `solar_resource/` — `pv_producer.py`, `exceedance.py`, `loss_model.py`, `long_term_trend.py`, `soiling_profile.py`, `bifacial_guard.py`, `source_quality.py`, `cashflow_adapter.py`, plus `__init__.py` (public surface) and `README.md`.

**Purpose:** The photovoltaic analogue of `wind_resource`: a standalone, config-driven producer that turns a fixed-tilt PV-system spec plus a measured site irradiance level into a bankable annual energy / capacity factor for a hybrid's `generation.technologies.solar` block, with a full P50/P75/P90 exceedance build-up, an itemised loss chain, and a frozen-export bridge into finance.

**Design reasoning:** It exists to give the hybrid case a defensible, reproducible solar CF without forcing the finance stack to carry a physics toolchain: `pvlib` is an opt-in `[solar]` extra imported lazily behind a `_require_pvlib()` fail-loud guard (CASPER), mirroring `py-wake` in `wind_resource` and WeasyPrint in `app.reports`. Every input is a typed `SolarResourceConfig` field read from a `resource.solar` block, with strict typo/schema rejection (CESSPIT); the producer is deterministic (fixed reference calendar year, no `Date.now`) so a config maps to one number. The domain deliberately splits into a VALIDATE surface (`validate_declared_solar_cf`, never mutates the scenario) and an OVERWRITE surface (`cashflow_adapter.solar_export_to_scenario_patch`, makes the modelled CF the billed driver), the two being explicit opposites the scenario flow selects between. The OVERWRITE bridge is a pure function over plain dicts that never imports `pvlib` — it consumes a frozen export, exactly as the wind adapter consumes a frozen `WindPipeline` export — so the base install and every CI lane run the hybrid finance case with no solar dependency. Shared numerics (the exceedance z-table, the loss-retention combiner) are reused from `analytics.core`/`analytics.wind` rather than forked, keeping wind and solar from drifting.

### Key modules

| Module | Role |
| --- | --- |
| `pv_producer.py` | The core pvlib pipeline. `compute_solar_aep` runs clear-sky GHI (Ineichen) for a fixed reference year → scales to the measured `annual_ghi_kwh_m2` → DISC decomposition to DNI → closure DHI → Hay-Davies plane-of-array transposition → Faiman cell temperature → PVWatts DC → PVWatts inverter clip at the AC nameplate → flat system-loss derate → annual AC energy. CF is reported against the DC nameplate (MWp). Optionally ingests a FROZEN hourly TMY (`tmy_path`, #529/SOLAR-6/12) to replace the clear-sky shape and scalar-temp assumption with measured hourly GHI/DNI/DHI and ambient temp/wind. Also hosts `validate_declared_solar_cf` (VALIDATE-only drift check) and `SolarResourceConfig`/`SolarAEPResult`. |
| `exceedance.py` | Pure (no pvlib, no numpy) P50/P75/P90 exceedance build-up. Turns the deterministic P50 energy into bankable exceedance levels from a config-first 1-sigma `SolarUncertaintyBudget` of PV categories (GHI dataset, transposition, simulation, soiling, module tolerance, thermal, availability). Root-sum-of-squares category combination with an optional uniform inter-category correlation; the interannual GHI term is divided by `sqrt(life_years)` for the project-life P90. Reads an optional `resource.solar.uncertainty` block (#604) via `solar_uncertainty_from_config`. |
| `loss_model.py` | Config-first itemised gross→net loss chain that decomposes the producer's flat `system_loss_pct` into named components (soiling, DC/AC wiring, mismatch, connection, nameplate, LID, transformer, transmission, curtailment, availability, grid availability). Reuses the technology-neutral retention engine from `analytics.wind.losses_model` (classifying each `*_pct` key as `reduction` or `uptime`); a loss-shaped key absent from the taxonomy raises rather than being dropped (CESSPIT). Taxonomy sourced from `config/defaults.yaml` with a built-in fallback. |
| `long_term_trend.py` | Report-only long-term GHI trend analysis (#727). Runs Mann-Kendall + Sen's-slope (Theil-Sen) plus OLS on an annual-GHI series, classifies decadal variability vs secular dimming/brightening, computes reference-period GHI (5yr / decade / 20yr / full record), recommends the forward-looking P50 GHI basis, and renders commentary + a "ResourceTrend" workbook sheet. Per-period AEP/CF are a first-order linear GHI-ratio proxy of the full-record P50 (not a pvlib re-run), surfaced as such in the artifact. Pure numpy/scipy, pvlib-free, network-free; changes no KPI or finance path. |
| `soiling_profile.py` | OPTIONAL time-varying soiling model (#743). Reduces a `resource.solar.soiling_profile` block (accumulation rate + wash cadence, optional clean floor / cap) to a single effective flat soiling percent — the energy-weighted mean over the wash cycle — that the producer substitutes for the flat `soiling_pct`. Default-off and byte-identical when the block is absent; applying it to the committed CF would be a user-gated re-baseline. |
| `bifacial_guard.py` | SOLAR-9 discipline guard (#743). Enforces that the financed/producer solar chain stays monofacial: `assert_monofacial_financed_cf` (called by the OVERWRITE bridge) inspects the export and target `resource.solar` for a bifacial-uplift marker (`bifacial_gain` / `bifacial_gain_pct` / `bifacial`) and raises `BifacialInFinancedChainError` rather than silently booking an un-validated rear-side gain. The illustrative `scripts/generate_solar_assessment_report.py` (which discloses `cf_mono` vs `cf_bifacial`) bypasses the bridge and is untouched. |
| `source_quality.py` | Solar resource source-quality grading (#743) — pure metadata, bills off nothing. Grades the irradiance evidence on four axes (measurement type, years of record, TMY source reputability, GHI dataset free-text) into a 0–1 `quality_score` and an A/B/C/D letter grade, emitted into the `solar_resource` provenance block only. Deliberately not wired to any billed field (the #587 P50-haircut lesson); an ungraded export records a candid low default grade so it never reads as investment-grade. |
| `cashflow_adapter.py` | The OVERWRITE finance bridge. A pure function over plain dicts (no pvlib import): `build_solar_cashflow_export` freezes a `SolarAEPResult`; `solar_export_to_scenario_patch` writes per-tech `capacity_mw` / `capacity_factor` (decimal) / `aep_gwh` and recomputes the blended `project.capacity_factor` from the per-tech sum so the engine's ±1% cross-check and `analytics.aep_reconciliation` guard stay satisfied (storage techs excluded via the engine's own predicate). Modes: `overwrite`, `fill_if_absent` (default), `validate_only`. Never rewrites `expected_results` / `resource.aep_summary_path` — the independent bankable references. |

### Academic / methodological grounding

- `pv_producer.py` — pvlib pipeline: Ineichen clear-sky model (`get_clearsky(model="ineichen")`), DISC decomposition to DNI (`pvlib.irradiance.disc`, documented to take the true, not refraction-corrected, zenith — SOLAR-7), Hay-Davies anisotropic transposition (`get_total_irradiance(model="haydavies")`, lender-preferred over the isotropic default), Faiman cell-temperature model (`pvlib.temperature.faiman`), and PVWatts DC + inverter models (`pvsystem.pvwatts_dc`, `inverter.pvwatts`). Standard deterministic year-1 P50 energy simulation; module degradation is deferred to the finance schedule to avoid double-counting (SOLAR-4).
- `exceedance.py` — IEC 61724-1 and IEA-PVPS Task 13 ("Uncertainties in Yield Assessments"): normal-distribution exceedance with a root-sum-of-squares category combination (optional uniform correlation), interannual term time-averaged by `sqrt(N)`. Uses the shared `analytics.core.exceedance` z-table (single table for wind and solar, parity-tested).
- `loss_model.py` — IEC 61724-1 / PVsyst DC→AC loss taxonomy (soiling, wiring, mismatch, LID, availability, etc.).
- `long_term_trend.py` — Mann-Kendall trend test + Sen's-slope / Theil-Sen estimator with OLS R² classification; bankable long-term reference framing per IEC 61724-1 / IEA-PVPS Task 13; global dimming/brightening context cited to Wild 2009 and IPCC AR6. Data source PVGIS SARAH-3 (Copernicus/EUMETSAT CM SAF), consumed frozen.
- `source_quality.py` — IEA-PVPS Task 13 evidence hierarchy: on-site pyranometry as gold standard, satellite GHI carrying larger bias/uncertainty (drives the measurement-type rubric).
- `soiling_profile.py` — Documented energy-weighted-mean-over-wash-cycle soiling model (accumulation rate + wash cadence); a lender-auditable in-house formulation, no external standard cited in-code.
- `bifacial_guard.py`, `cashflow_adapter.py` — No formal academic grounding; discipline guard and contract plumbing (SOLAR-9 audit disposition #485 and the frozen-export finance bridge, respectively).

### Interfaces, optional extras, and limitations

- **Consumes:** a scenario's `resource.solar` block (site coords, `annual_ghi_kwh_m2`, fixed-tilt PVWatts system spec, `dc_ac_ratio`, `system_loss_pct`, optional `tmy_path`, optional `uncertainty` / `soiling_profile` / `source_quality` sub-blocks) via `SolarResourceConfig.from_scenario`. **Produces:** a `SolarAEPResult` (annual AC energy, DC-nameplate CF, specific yield), a `SolarExceedanceResult` (P50/P75/P90), an itemised net-loss factor, a provenance/source-quality block, a trend export block, and — after freezing — a `SolarCashflowExport` dict that patches per-tech and blended `capacity_factor`.
- **Optional extra:** `pip install -e '.[solar]'` (pvlib) powers only the physics producer (`pv_producer`). `exceedance`, `loss_model`, `soiling_profile`, `bifacial_guard`, `source_quality` and `cashflow_adapter` are pvlib-free; solar tests are gated behind `pytest.importorskip('pvlib')` and skip on the default install.
- **Honesty boundary — VALIDATE vs OVERWRITE:** by default the financed run bills off the config-declared `generation.technologies.solar.capacity_factor` (the P50 stays the human-curated driver); making the modelled CF the billed quantity is an explicit OVERWRITE the scenario flow must select. `expected_results` and `resource.aep_summary_path` are never rewritten by the adapter — re-baselining bankable references is a deliberate, audited scenario edit.
- **Default-off / user-gated levers:** the `uncertainty` (#604), `soiling_profile` (#743) and `source_quality` (#743) blocks are all byte-identical when absent; applying a soiling profile, a source-quality-driven haircut, or a TMY re-baseline (SOLAR-6/12, #529) to the committed CF is a user-gated re-baseline of the same class as the wind #587 no-EYA haircut policy (which deliberately does not port to solar). The committed hybrid CF is the frozen monofacial PVGIS-TMY yield (≈0.1685 / ≈1476 kWh/kWp); the clear-sky default on the same block yields ≈0.179 / ≈1568.
- **Disclosed limitations:** the clear-sky default assumes a scaled clear-sky year shape (removed only when a frozen hourly TMY is supplied); `long_term_trend` per-period energy is a first-order linear GHI-ratio proxy, not a per-period pvlib re-run, and is labelled as such; bifacial rear-side uplift is refused in the financed chain (SOLAR-9) and appears only in the standalone illustrative report, which discloses `cf_mono` vs `cf_bifacial` side by side.

## Web service, async jobs & lender report

**Path(s):** `app/api/` (`main.py`, `auth.py`, `jobs_router.py`, `surface.py`, `responses.py`, `config.py`); `app/jobs/` (`worker.py`, `runner.py`, `redis_store.py`, `store.py`, `sse.py`, `models.py`, `config.py`); `app/reports/` (`renderer.py`, `report_model.py`, `report_config.py`, `capital_risk_emit.py`, `grid_screening_emit.py`, `interaction_grid_emit.py`, `tech_comparison_emit.py`, `wind_rose_plot.py`); `app/services/` (`pipeline_service.py`, `report_global_sa.py`, `report_tornado.py`); `app/web/` (`routes.py`, `auth_cookie.py`); `app/models/inputs.py`; and the legacy `api/` package (`pipeline_api.py`, `sensitivity_api.py`, `path_safety.py`).

**Purpose:** This domain is the productization layer: it exposes the canonical v14 finance engine over an authenticated HTTP API, an HTMX web wizard, and an asynchronous live-ERA5 job path, and it renders the run into a lender-grade HTML/PDF/XLSX report. It adds no finance logic — every route and emitter is a projection of, or delegation to, the canonical pipeline.

**Design reasoning:** It sits at the outermost architectural ring, above the service seam (`app.services.pipeline_service.run_finance_case` / `run_integrated_case`) which is the single backend entry into the canonical `run_v14_pipeline` gateway; nothing here re-derives IRR/NPV/DSCR (ARCH-02/CCCDIR — all modelling stays in `analytics`/`finance`). The public HTTP surface is version-pinned under `/v1` (#841 contract freeze: breaking changes land as `/v2`, never a mutation of `/v1`) and the client-facing response *shape* carries a separate SemVer `API_CONTRACT_VERSION`, both frozen by contract tests. Optional capabilities (WeasyPrint PDF, arq+Redis jobs, matplotlib plots, grid screens) are guarded at call-time and fail loud or degrade to omission rather than at import (CASPER); config is read fail-closed from the environment with documented defaults (CESSPIT). A notable structural decision is the stdlib-only auth and form-parsing (hand-rolled HS256 JWT + PBKDF2, `urllib.parse.parse_qsl` instead of `python-multipart`) specifically to avoid disturbing the strict `requirements.txt` lock and the `pip-audit` gate.

Absence degrades to an omitted section or a fail-loud `ReportDependencyError`/`RuntimeError`, never a silent stub.
- **Default-off levers the code discloses:** the four report emitters (`capital_risk`, `grid_screening`, `interaction_grid`, `tech_comparison`) are opt-in and default-off from the batch CLI — the synchronous HTTP report route passes `None` for each, so committed-scenario output stays byte-identical; the async `redis` jobs backend is opt-in via `DUTCHBAY_JOBS_BACKEND` (default `memory`, byte-identical to pre-#663).
- **Honesty boundaries / caveats:** the grid-screening section is **advisory only** (`bankable=False`, never feeds CFADS/IRR/DSCR) and carries an un-suppressible screening-not-bankable + EMT-gap caveat with no config toggle to remove it; capital-risk MC forces `allow_toy_fallback:false` (raises rather than fabricating a metric); global-SA omits a section rather than render an engine-flagged (`nan_poisoned`/`flat_metric`) zeroed driver as a false "no influence" claim.
- **Structural limitations the code states:** the synchronous route timeout bounds the *client wait*, not the compute (the worker thread cannot be force-cancelled, so a timed-out run keeps counting against the concurrency bound until it finishes); the sync wizard path keeps the base variant's frozen `aep_summary` (capacity/CF edits do not re-derive AEP — use the async live-ERA5 path for that); and out of code scope (user-held ops per #858): JWT revocation/`jti` denylist/rotation, the secret store, and TLS termination — a leaked token stays valid until `exp`.

## Operational, CI & Analysis Scripts

**Path(s):** `scripts/` — canonical Hydra/CLI runners (`run_wind_analysis_v14.py`, `run_fx_calibration.py`, `run_global_sensitivity.py`, `run_multi_tech_tornado.py`, `run_epc_margin.py`, `generate_solar_assessment_report.py`); release/changelog tooling (`compile_changelog.py`, `build/`, `provision_web_secrets.py`); CI guards (`scripts/ci/` — `check_legacy_imports.py`, `ci_structure_check.py`, `model_guard.py`, `go_with_the_flow_ci.py`); and ERA5/data tooling (`inspect_era5.py`, `process_era5_wind_data.py`, `codebase_datalake_ingress.py`).

**Purpose:** The operator-facing surface of the model: thin command-line entry points that drive the analytics/finance engines for a scenario, plus the local CI, release-packaging and data-ingestion utilities that keep the repository governable and reproducible. None of these scripts contain model math; they load configuration, call the canonical library routines, and emit CSV/JSON/PDF/stdout artifacts.

**Design reasoning:** The scripts exist so that every analytical routine is reachable without importing internals ad hoc, and so each runner honors the same contracts the library enforces. Runners are deliberately "thin CLIs" over library functions (e.g. `run_multi_tech_tornado.py` wraps `analytics.portfolio.multi_tech_tornado`, `run_global_sensitivity.py` wraps `analytics.sensitivity.global_sa`), routing all evaluation through the `evaluate_with_overrides` gateway (ARCH-04/CCCDIR) rather than recomputing IRR/NPV locally (ARCH-02 keeps that in `finance/irr.py`). CLI conventions are governed by GWTF: the wind runner is Hydra-only (R3) and JSON-first (CLI-03), while argparse-bearing runners are the sanctioned exceptions, and secret/provisioning paths (`provision_web_secrets.py`) forbid argparse/Typer/`input()` (R3/R4/CST-01) and read from the environment instead. Optional heavy dependencies (reportlab, matplotlib, pvlib, rasterio, xarray) are CASPER-gated and lazily imported, so the base finance stack never depends on the reporting or ERA5 tooling. The CI guards are self-checking (`check_legacy_imports.py` documents a fixed `parents[2]` root-path bug that had made the guard pass vacuously), reflecting the "verify the guard actually guards" discipline.

### Academic / methodological grounding

- `process_era5_wind_data.py` — Power-law (wind-shear) vertical extrapolation `ws(h) = ws(h_ref)·(h/h_ref)^α`, with the shear exponent α fitted from two reanalysis heights (10 m, 100 m) and clipped to the coastal 0.05–0.40 range; used to lift ERA5 wind to the 150 m hub height.
- `run_global_sensitivity.py` — SALib Morris (elementary-effects screening), Sobol (first-order `S1` vs total-order `ST` variance decomposition), and PAWN (moment-independent, KS-statistic) methods; Campolongo/Ruano spread-maximising optimal-trajectory selection for Morris (with OSeMOSYS "10-from-100" trajectory guidance). Used for variance-based global sensitivity over the Monte-Carlo driver set.
- `generate_solar_assessment_report.py` — pvlib chain for the solar producer: DISC model for DNI (`pvlib.irradiance.disc`), Faiman cell-temperature model (`pvlib.temperature.faiman`), and the PVWatts DC/inverter model (`pvlib.pvsystem.pvwatts_dc` / `pvlib.inverter.pvwatts`); Latin-Hypercube Monte Carlo for P10/P50/P90 return exceedance; IEA "capital costs of utility-scale solar PV in emerging economies" (~USD 1,120/kW) as the capex benchmark. Bankable resource anchored to Solargis GHI/PVOUT references.
- `run_wind_analysis_v14.py` — Reports Weibull-fitted resource statistics and P50/P75/P90 AEP exceedance levels (computation lives in the `wind_resource` library it calls, not in the script itself).
- CI guards, `build/`, `compile_changelog.py`, `codebase_datalake_ingress.py`, `provision_web_secrets.py`, `run_epc_margin.py`, `run_fx_calibration.py` — No formal academic grounding; orchestration, packaging and contract plumbing. (`compile_changelog.py` follows the towncrier/scriv + Keep-a-Changelog convention; `provision_web_secrets.py` uses PBKDF2-HMAC-SHA256 password hashing — engineering conventions, not cited literature.)

### Interfaces, optional extras, and limitations

- **Consumes:** scenario YAML (`scenarios/*.yaml`) or Hydra `conf/` groups, the provenance-pinned FX vintage, ERA5 NetCDF files, and `changelog.d/` / manifest fragments. **Produces:** JSON (wind assessment / CI artifacts), CSV (sensitivity, tornado, datalake indexes), a >10,000-word solar PDF, packaged release zips, and stdout economics — all model-derived, never hand-entered.
- **Opt-in install extras:** the solar report needs `.[report]` (reportlab), plus `.[solar]` (pvlib/scipy) and `.[gis]` (rasterio); matplotlib powers charts; ERA5 tooling needs xarray/netCDF; these are CASPER-gated and lazily imported so the core finance stack never pulls them in.
- **Network-touching, off by default:** `run_fx_calibration.py --validate`/`--refresh` and the wind runner's ERA5 download reach out to BIS/FRED/CDS; the deterministic path uses only the pinned vintage. `--refresh` is explicitly a deliberate dated re-pin, not an automatic update.
- **Honesty boundaries the code itself states:** the multi-tech tornado warns that a naive one-way sweep is a "phantom/crash" and that `min_dscr` is structurally flat (dual-DSCR sculpting) so covenant stress must be read off `balloon_pct`; the global-SA docstring flags that Sobol misbehaves on skewed/covenant-pinned KPIs and points to PAWN and `docs/SENSITIVITY_DECISION_TREE.md`. The solar report's own narrative surfaces a negative-return finding (project IRR never reaches the cost of capital) rather than masking it.
- **Governance levers in-code:** `provision_web_secrets.py` refuses to emit a blank credential (exit 2) and enforces the 32-char production JWT-secret floor; `compile_changelog.py --check` and the `scripts/ci/` guards return non-zero to fail CI; global-SA/tornado runners are opt-in and documented as additive and KPI-neutral (they do not move canonical outputs).

## Limitations and bankability notes

The model is complete and correctly implemented across its methodology, and it discloses its
own limitations rather than concealing them (the canonical equity IRR is reported as negative,
not clipped). The items below are the substantive limitations a lender-facing run should weigh;
each is disclosed in the code or in the `model_limitations` configuration block, and each is
examined in full in the separately delivered deep-research credibility report.

- **Wind resource input basis.** The committed headline AEP rests on single-cell ERA5
  reanalysis with no on-site measurement mast; this is a pre-measurement basis under
  IEC 61400-15-1 / MEASNET. A Measure-Correlate-Predict module (`wind_resource/mcp.py`) exists
  but is not wired into the committed path. Treat P50/P90 as pre-measurement until a real mast
  campaign is run through the MCP module.
- **Debt service reserve account.** The DSRA is modelled as a fund-at-close sources-and-uses
  item with no dynamic operating draw and release to cure a low-DSCR year, and it is opt-in.
- **Monte Carlo default.** The Monte Carlo engine allows a toy fallback by default
  (`allow_toy_fallback=True`); a failed trial substitutes tagged, counted placeholder KPIs. A
  lender or production run should set this to `false`.
- **Default breach probability.** Because debt is sculpted to the covenant floor, the default
  DSCR-breach probability is structurally near zero; the honest breach distribution requires
  the opt-in `monte_carlo.fixed_debt_stress` path.
- **Statutory and structural levers.** Several levers (dividend withholding, interest
  withholding gross-up, senior credit-support fees, import levies, P90 debt binding, FX
  hedging) default off. Confirm which are enabled before citing headline KPIs.
- **Grid study status.** The grid module is a design-stage screening study, not the
  utility-accepted bankable connection study; cases it cannot assert are reported as an
  explicit "not run".
